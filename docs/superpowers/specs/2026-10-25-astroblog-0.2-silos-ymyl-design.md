# @didierp/astroblog 0.2.0: silos y señales YMYL (diseño)

Fecha: 2026-10-25
Estado: borrador para revisión
Consumidor que lo motiva: web HipotecaClara (`D:/proyects/nicho-hipotecas-espana`)

## 1. Objetivo

Ampliar la librería para que sirva a webs de nicho YMYL (finanzas, salud, legal) organizadas por silos temáticos, sin romper los sitios 0.1. Es una versión **minor** y todo lo nuevo es opcional: un sitio 0.1 que actualiza a 0.2 sin cambiar su configuración genera exactamente el mismo `dist/`.

### Criterios de éxito

- Con `permalinks: 'silo'`, los posts se publican en `/<categoria>/<slug>/` y el índice de cada categoría en `/<categoria>/`. Nada se publica en `/blog/` ni en `/categoria/`.
- Breadcrumbs, PostCard, PostHeader, RSS, sitemap y canonical generan las URLs de silo sin que el consumidor cambie nada.
- Un post puede declarar revisor, FAQ y fuentes. Se muestran en la página y se emiten como JSON-LD (`FAQPage`, `reviewedBy`).
- El consumidor puede crear páginas propias (home a medida, metodología, calculadoras) con el layout del sitio importando `@didierp/astroblog/layouts`.
- Los fixtures y tests de 0.1 pasan sin cambios.

### Fuera de alcance

- Colección de autores con varias personas (se usa el autor único de la configuración más revisores definidos en ella).
- Contenido multi-idioma, SSR, newsletter y series (siguen fuera, como en 0.1).
- Silos anidados en más de un nivel (`/a/b/slug/`).
- Componentes MDX globales (sin mapeo automático; se siguen importando en cada `.mdx`).

## 2. Permalinks por silo

### Configuración

```ts
permalinks: 'blog' | 'silo' = 'blog'
```

### Rutas

En modo `'silo'`, `resolveRoutes` (`lib/routes.ts`) deja de inyectar `post` (`/blog/[...slug]`) y `category` (`/<categoria>/[cat]/[...page]`) e inyecta **una sola ruta** `/[...path]` con el entry nuevo `routes/silo.astro`. Su `getStaticPaths` genera:

| Ruta generada | Contenido | Props |
|---|---|---|
| `/<cat>/` | Página 1 del listado de la categoría | `kind: 'category'` |
| `/<cat>/<pagina>/<n>/` (n ≥ 2) | Página n del listado (`<pagina>` = slug `page`, por defecto `pagina`) | `kind: 'category'` |
| `/<cat>/<slug>/` | Post | `kind: 'post'` |

`silo.astro` renderiza `TaxonomyLayout` o `PostLayout` según `kind`, reutilizando la lógica actual de `routes/category.astro` y `routes/post.astro`. No se duplica el render: se extrae a funciones de `lib/blog.ts`.

Usar una sola ruta evita que Astro tenga dos rutas dinámicas del mismo nivel compitiendo por la misma URL. Las rutas estáticas del consumidor (p. ej. `src/pages/calculadoras/index.astro`) e institucionales (`/acerca/`) tienen prioridad sobre `/[...path]`, según el orden de prioridad de rutas de Astro.

### Derivación de URLs

- `<cat>` = `slugify(post.data.category)` (con `slugify` de `lib/posts.ts`).
- `<slug>` = último segmento de `post.id`. El fichero puede estar en `src/content/blog/<cat>/<slug>.md` o en la raíz; la carpeta no decide la URL, la decide `category`.
- Helper nuevo `postPath(config, post): string` en `lib/routes.ts`. Devuelve `/blog/<id>/` en modo `blog` y `/<cat>/<slug>/` en modo `silo`. Sustituye a `routePath(config, 'post', post.id)` en `PostCard.astro`, `routes/rss.xml.ts` y en la construcción del canonical de `PostLayout`.
- `virtual:astroblog/routes`: en modo silo, `paths.category` vale `'/'`. `taxonomyPath` se corrige para que una sección raíz produzca `/<cat>/` (hoy `section && s` descarta la cadena vacía resultante).

### Validaciones

Las colisiones dependen de los posts, así que se comprueban en `loadPosts` (`lib/blog.ts`) y no en `validateConfig`. Cada una es un error de build con mensaje en `es`/`en`:

- El slug de una categoría coincide con un slug reservado: institucionales (`acerca`, `contacto`, `privacidad`, `cookies`, `terminos`, `aviso-legal`), `buscar`, `etiqueta`, `autor`, `pagina`, `404`, o cualquier valor sobrescrito en `slugs`.
- Dos posts producen el mismo `/<cat>/<slug>/`.
- El slug de un post es igual al slug `page` (`pagina`), porque chocaría con la paginación.

Además, si `permalinks` vale `'silo'` y `routes.post` o `routes.category` están en `false`, se avisa (warning) de que esa opción se ignora y basta con no usar silos.

## 3. Campos YMYL en el frontmatter

`blogSchema` (`content.ts`) añade estos campos, todos opcionales:

```ts
reviewer?: string;                        // id de config.reviewers
reviewedDate?: Date;                      // z.coerce.date()
faq?: { q: string; a: string }[];         // a: texto plano o Markdown en línea
sources?: { title: string; url: string }[];
```

Validación en `loadPosts`: error si `reviewer` no existe en `config.reviewers`.

## 4. Autor, revisores y aviso legal

Cambios en `schema/config.ts`:

```ts
author?: { name; email?; url?; avatar?; bio?: string; jobTitle?: string; sameAs?: string[] };
reviewers?: Record<string, { name: string; jobTitle?: string; url?: string; bio?: string; avatar?: string }>;
disclaimer?: string;      // se muestra al final de cada post
seo?: { articleType?: 'BlogPosting' | 'Article' };   // por defecto 'BlogPosting'
```

- `AuthorBox` y la página `/acerca` (plantilla `legal/*/about.astro` y `legal/AuthorCard.astro`) muestran `jobTitle` y `bio` cuando existen.
- No hay rutas nuevas para revisores. Si el revisor tiene `url`, se enlaza a ella.

## 5. Render y SEO

### Render en `PostLayout`

1. `PostHeader`: añade "Actualizado el <fecha>" cuando hay `updatedDate`, y "Revisado por <nombre> · <jobTitle>" cuando hay `reviewer` (más `reviewedDate`, si existe).
2. Tras `<Content />`, en este orden: `Faq` si hay `faq`, `Sources` si hay `sources`, `ReviewedBy` si hay `reviewer`, y el `disclaimer` si está configurado. Después siguen `AuthorBox`, `ShareLinks`, `RelatedPosts` y `Comments`, como ahora.
3. `Faq`, `Sources` y `ReviewedBy` son componentes nuevos sustituibles: se añaden a `COMPONENT_KEYS`, a `components.ts` y a `virtual:astroblog/components`.
   - `Faq` usa `collapse` de daisyUI (con `details`/`summary`, accesible sin JavaScript) agrupados con `join join-vertical`.
   - `Sources` es una lista con `rel="nofollow noopener"` y `target="_blank"`.
4. Textos nuevos de la interfaz en `i18n/es.ts` y `i18n/en.ts`: `updatedOn`, `reviewedBy`, `faqTitle`, `sourcesTitle`, `disclaimerTitle`.

### JSON-LD (`lib/seo.ts`)

- `jsonLdPost` recibe `type` (`config.seo.articleType`), y el autor incluye `jobTitle` y `sameAs` cuando existen.
- `jsonLdFaq(faq)` → `{ "@type": "FAQPage", mainEntity: [{ "@type": "Question", name, acceptedAnswer: { "@type": "Answer", text } }] }`. Solo se emite cuando hay `faq`.
- Cuando hay revisor: `{ "@type": "WebPage", url, reviewedBy: { "@type": "Person", name, jobTitle?, url? }, lastReviewed? }`.
- `PostLayout` pasa el conjunto en la prop `jsonLd` de `BaseLayout`, que ya la acepta.

## 6. Layouts exportados

- Nuevo export en `package.json`: `"./layouts": "./layouts.ts"`, que reexporta `BaseLayout` y `PageLayout`.
- Se documenta como API pública la interfaz de props de `BaseLayout`: `title`, `description`, `image?`, `type?`, `breadcrumbs?`, `jsonLd?`, `noindex?`. `PageLayout` añade `updatedDate?` y renderiza contenido con `prose`.
- Se añade la prop `noAds?: boolean` a ambos layouts para que una página propia, como una calculadora, decida dónde poner sus `AdSlot`.
- Caso de uso documentado: `routes: { home: false }` + `src/pages/index.astro` con `BaseLayout`.
